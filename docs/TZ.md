# ТЗ: Atlas — навигатор по проекту для нейросетей

Nov 23, 2026 · @Дмитрий

## 1. Общие сведения

Atlas — локальное десктопное приложение, которое индексирует проект, строит граф связей между его частями и отдаёт нейросети компактную карту вместо чтения файлов целиком. Человеку то же самое показано в интерфейсе в духе Obsidian: граф, дерево файлов, просмотр кода и заметок.

### 1.1. Проблема

- Агент тратит большую часть токенов на разведку: серия поисков, чтение файлов целиком, повторные чтения.
- Каждый вызов инструмента заново оплачивает весь накопленный контекст.
- Вывод сборок, тестов и логов раздувает контекст шумом.
- Человеку трудно увидеть, что именно нейросеть «знает» о проекте и что она читала.

### 1.2. Цели

1. Детерминированно (без нейросети) построить и держать актуальным индекс проекта: файлы, символы, связи.
2. Дать нейросети 5–7 компактных инструментов навигации по протоколу MCP, чтобы она спускалась от карты к конкретной функции только по необходимости.
3. Показать человеку интерактивный граф, просмотр файлов и журнал того, что запрашивала нейросеть; по запросу собирать из индекса, git и журнала отчёт в формате Markdown: что это за проект, как он устроен и что в нём сделано (раздел 7.9).
4. Измеримо снизить расход токенов на навигационных задачах. Целевое значение: не менее 40% экономии на проектах от 500 файлов при том же качестве результата. Цифра — рабочая гипотеза, подтверждается замером по разделу 14.
5. Работать полностью локально: код проекта не покидает компьютер, кроме тех кусков, которые клиент нейросети сам запросил.

### 1.3. Нецели (в первой версии)

- Атлас не пишет и не рефакторит код проекта сам и не двигает файлы.
- Не является IDE и не заменяет редактор: просмотр файлов только для чтения.
- Не содержит собственной нейросети и не требует облачного сервиса; саммари модулей через нейросеть — опциональная функция, выключенная по умолчанию.
- Не поддерживает совместную работу нескольких пользователей и облачную синхронизацию индекса.

### 1.4. Ключевые сценарии

| № | Сценарий | Кто | Результат |
| --- | --- | --- | --- |
| 1 | Открыть папку проекта, дождаться индексации | Разработчик | Видит граф, дерево файлов, статистику |
| 2 | Подключить Atlas к Claude или другому MCP-клиенту одной кнопкой | Разработчик | Клиент получает инструменты навигации |
| 3 | Нейросеть спрашивает «кто вызывает функцию X» | Нейросеть | Короткий список вызовов вместо поиска по тексту |
| 4 | Нейросеть запрашивает контекст задачи одним вызовом | Нейросеть | Функция, сигнатуры зависимостей, вызывающие, тест |
| 5 | Человек просматривает граф и находит «узлы-хабы» и мёртвый код | Разработчик | Понимание структуры, список подозрительных узлов |
| 6 | Человек смотрит журнал вызовов и расход токенов | Разработчик | Видит, что читала нейросеть и сколько это стоило |
| 7 | Файл изменён, индекс обновляется сам | Система | Карта остаётся актуальной за секунды |
| 8 | Человек закрывает часть проекта от нейросети | Разработчик | Выбранные пути не попадают в ответы |

## 2. Пользователи, роли и термины

У системы два типа потребителей: человек, который смотрит и настраивает, и нейросеть, которая запрашивает данные через протокол. Ниже их роли и словарь, которым пользуется весь документ.

### 2.1. Роли

| Роль | Что делает | Права |
| --- | --- | --- |
| Разработчик (владелец проекта) | Открывает проект, настраивает исключения, смотрит граф и журнал | Полный доступ к настройкам и данным |
| Нейросеть-клиент (через MCP) | Запрашивает карту, символы, связи, куски кода | Только чтение, в рамках бюджета и списка допустимых путей |
| Наблюдатель (опционально, позже) | Смотрит граф и статистику без настроек | Только чтение интерфейса |

### 2.2. Термины

| Термин | Значение |
| --- | --- |
| Проект | Папка на диске, которую пользователь добавил в Atlas |
| Индекс | База данных (SQLite) с файлами, символами и связями проекта |
| Узел | Элемент графа: каталог, файл, символ (класс, функция, метод, константа), тест, документ |
| Ребро | Связь между узлами: содержит, импортирует, вызывает, наследует, тестирует, упоминает |
| Символ | Именованная сущность в коде с позицией в файле и сигнатурой |
| Карта | Сжатое текстовое представление графа с лимитом по токенам, которое получает нейросеть |
| Уровень детализации (LOD) | Одна из пяти ступеней: от карты проекта до тела функции |
| Бюджет | Максимум токенов, который один вызов инструмента может вернуть |
| Хаб | Узел с аномально большим числом входящих связей |
| Сессия | Подключение одного MCP-клиента, в рамках которой ведётся журнал и счётчик токенов |

## 3. Архитектура системы

Система состоит из пяти программных компонентов. Интерфейс и MCP-сервер не знают друг о друге и работают через общее ядро, поэтому человек и нейросеть всегда видят одни и те же данные.

Индексатор — единственный компонент, который пишет в базу при изменении проекта; ядро читает базу, считает ранги и собирает ответы для обоих входов.

### 3.1. Компоненты

| Компонент | Ответственность | Где живёт |
| --- | --- | --- |
| Индексатор | Обход файлов, разбор, наблюдение за изменениями, запись в базу | `atlas-indexer`, `atlas-langs` |
| Хранилище | Схема, миграции, транзакции, полнотекстовый поиск | `atlas-store` |
| Ядро | Построение графа, ранжирование, поиск, бюджеты, генерация карты и отчёта | `atlas-core` |
| MCP-сервер | Протокол, описания и схемы инструментов, форматирование ответов, журнал | `atlas-mcp` |
| Интерфейс | Окно приложения: граф, файлы, панели, настройки | `app/ui`, `app/electron` |

### 3.2. Потоки данных

1. Пользователь добавляет проект; индексатор обходит файлы с учётом исключений и пишет узлы и рёбра в базу.
2. Наблюдатель замечает изменение файла; индексатор пересчитывает затронутые узлы и обновляет ранги.
3. Нейросеть вызывает инструмент MCP; сервер передаёт запрос ядру, ядро читает базу и при необходимости тело символа с диска, обрезает результат по бюджету и возвращает плотный текст.
4. Каждый вызов записывается в журнал; интерфейс получает событие и обновляет подсветку на графе и панель расхода.
5. Пользователь запрашивает отчёт; ядро собирает данные из индекса, git и журнала и формирует Markdown-файл.

### 3.3. Процессы

- Фоновый процесс (`atlas-daemon`) держит индекс, наблюдатель и MCP-сервер; живёт, пока открыт хотя бы один проект, и показывается значком в области уведомлений.
- Окно приложения — отдельный процесс, подключается к фоновому и может быть закрыто без остановки индексации.
- Команда `atlas mcp` для клиентов, запускающих сервер сами, подключается к уже работающему фоновому процессу или запускает его.

## 4. Индексатор

Индексатор — обычный код без нейросети: он обходит проект, разбирает файлы синтаксическим парсером и пишет результат в базу. Он должен быть детерминированным: один и тот же проект всегда даёт один и тот же индекс.

### 4.1. Что извлекается

1. Дерево каталогов и файлов с размером, хешем содержимого, языком и временем изменения.
2. Символы: классы, интерфейсы, функции, методы, константы, типы, с диапазоном строк, видимостью, сигнатурой и докстрингом.
3. Импорты и зависимости между файлами и модулями.
4. Вызовы и ссылки между символами там, где их можно определить статически.
5. Связь «тест → тестируемый код» по именам, импортам и расположению.
6. Документы: Markdown, README, ADR; заголовки и ссылки между ними как отдельные узлы.
7. Метаданные из git: частота изменений файла, дата последнего изменения, авторы (если репозиторий есть).

### 4.2. Парсинг и языки

- Основа: tree-sitter для синтаксического разбора, плюс по возможности подключение языковых серверов (LSP) для точного разрешения ссылок.
- Первая версия (MVP): TypeScript/JavaScript, Python, Rust, Go, Markdown.
- Вторая волна: Java, C#, C/C++, Kotlin, PHP, Ruby, конфиги (JSON, YAML, TOML).
- Для неподдерживаемых языков файл всё равно попадает в индекс как узел с размером и путём, символы не извлекаются.
- Язык добавляется как плагин: набор запросов tree-sitter для символов, импортов и вызовов в отдельном файле, без изменения ядра.

### 4.3. Обновление индекса

- Первичная индексация идёт параллельно по ядрам процессора, с индикатором прогресса.
- Файловый наблюдатель реагирует на изменения; события собираются в пакет с задержкой около 300 мс и обрабатываются одним проходом.
- Файл пересчитывается, только если изменился хеш содержимого; рёбра, зависящие от изменённых символов, пересобираются точечно.
- При смене git-ветки или массовых изменениях запускается выборочная переиндексация по списку изменённых файлов из git.
- Каждая запись индекса несёт версию схемы и версию парсера; при их смене затронутые файлы переиндексируются автоматически.
- Если индекс не успевает за изменениями, ответы MCP помечаются признаком `stale: true` вместе со временем последнего обновления.

### 4.4. Исключения

- По умолчанию учитываются `.gitignore` и собственный файл `.atlasignore` с тем же синтаксисом.
- Всегда исключаются: `node_modules`, `vendor`, `target`, `dist`, `build`, `.git`, бинарные файлы, lock-файлы, минифицированные бандлы и сгенерированный код (по признакам в заголовке и по шаблонам имён).
- Файлы больше 1 МБ индексируются только как узлы без разбора содержимого; порог настраивается.
- Список исключений виден и редактируется в интерфейсе, изменение применяется без перезапуска.

### 4.5. Ограничения статического анализа

Динамические вызовы, рефлексия, внедрение зависимостей и вызовы через строки статически не определяются. Такие рёбра помечаются уровнем уверенности (`certain`, `likely`, `guess`), а в интерфейсе и ответах MCP показывается, какие связи могут быть неполными.

## 5. Модель данных

Индекс хранится в одном файле SQLite на проект (`.atlas/index.db` в папке проекта или в каталоге данных приложения, на выбор пользователя). Отдельная графовая база не нужна: граф строится запросами по таблицам узлов и рёбер.

### 5.1. Таблицы

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `project` | Метаданные проекта | id, корневой путь, версия схемы, время последней индексации |
| `node` | Все узлы графа | id, kind, path, name, parent\_id, lang, hash, line\_start, line\_end, signature, doc\_summary, tokens\_est, rank |
| `edge` | Связи между узлами | src\_id, dst\_id, kind, confidence, weight |
| `file_meta` | Данные о файле | node\_id, size, mtime, git\_changes\_30d, last\_commit, is\_test, is\_generated |
| `summary` | Кэш текстовых описаний (опционально) | node\_id, content\_hash, text, model, created\_at |
| `search_fts` | Полнотекстовый индекс (FTS5) | name, signature, doc, path |
| `call_log` | Журнал запросов нейросети | session\_id, time, tool, args, tokens\_out, node\_ids |
| `settings` | Настройки проекта | key, value |

### 5.2. Типы узлов (`node.kind`)

`dir`, `file`, `module`, `class`, `interface`, `function`, `method`, `constant`, `type`, `test`, `doc`, `config`.

### 5.3. Типы рёбер (`edge.kind`)

| Вид | Смысл | Уверенность |
| --- | --- | --- |
| `contains` | Каталог содержит файл, файл содержит символ | certain |
| `imports` | Файл или модуль импортирует другой | certain |
| `calls` | Символ вызывает символ | certain / likely / guess |
| `extends` | Класс наследует или реализует | certain |
| `tests` | Тест проверяет символ или файл | likely |
| `mentions` | Документ или комментарий упоминает символ | guess |
| `co_changes` | Файлы часто меняются вместе (из git) | likely |

### 5.4. Правила

- Идентификатор узла стабилен: строится из пути и квалифицированного имени, поэтому ссылки в журнале и закладки не ломаются после переиндексации.
- Тела функций в базе не хранятся: они читаются с диска по `path` и диапазону строк в момент запроса, чтобы не дублировать код и не отдавать устаревшее.
- Оценка размера в токенах (`tokens_est`) считается при индексации и используется для бюджетов.
- Миграции схемы выполняются автоматически, перед миграцией делается копия базы.
- Индекс можно безопасно удалить: он полностью восстанавливается из исходников.

## 6. Граф знаний

Граф даёт нейросети возможность спускаться от общего к частному: она получает карту, выбирает область и запрашивает только нужные детали. Те же уровни использует интерфейс при приближении графа.

### 6.1. Уровни детализации (LOD)

| Уровень | Что возвращается | Ориентир по размеру |
| --- | --- | --- |
| L0 · Карта проекта | Модули верхнего уровня, их назначение, главные хабы | до 500 токенов |
| L1 · Модуль | Файлы модуля и ключевые символы с одной строкой описания | до 800 токенов |
| L2 · Файл | Сигнатуры и докстринги всех символов файла | до 1 500 токенов |
| L3 · Символ | Тело одной функции или класса, при необходимости со свёрнутыми вложенными блоками | по размеру символа, с обрезкой по бюджету |
| L4 · Окружение | Вызывающие, вызываемые, наследники, связанные тесты символа | до 1 000 токенов |

Ориентиры — значения по умолчанию; фактический лимит задаётся бюджетом вызова (раздел 8.3).

### 6.2. Ранжирование

Чтобы карта влезала в лимит, узлы сортируются по важности. Оценка складывается из нескольких сигналов:

1. PageRank по рёбрам `imports` и `calls`: чем больше на узел ссылаются важные узлы, тем он важнее.
2. Частота изменений в git за последние 30 дней: «горячий» код показывается подробнее.
3. Близость к текущему контексту: файлы, которые нейросеть уже запрашивала в сессии, и их соседи получают надбавку.
4. Публичность символа: экспортируемые функции важнее приватных.
5. Штраф для тестов, сгенерированного кода и устаревших узлов.

Веса сигналов хранятся в настройках проекта и пересчитываются при каждом обновлении индекса. В интерфейсе размер и яркость узла на графе отражают итоговый ранг.

### 6.3. Группировка

- Модули определяются по структуре каталогов; если структура плоская, применяется кластеризация по плотности рёбер (алгоритм Лувена).
- Каждая группа получает имя из общего префикса пути или самого частого имени символа; пользователь может переименовать группу вручную, имя сохраняется.
- Хабы (узлы с входящей степенью выше порога) выделяются в отдельный список: это кандидаты на рефакторинг и главные точки входа для понимания проекта.

### 6.4. Аналитика графа (для человека)

- Циклические зависимости между модулями.
- Узлы без входящих связей (возможный мёртвый код) с оговоркой о динамических вызовах.
- Файлы, которые часто меняются вместе, но не связаны импортами (скрытая связность).
- Самые большие файлы и функции по числу токенов.

### 6.5. Описания модулей (опционально)

Описание можно взять из докстрингов и README (по умолчанию) или сгенерировать нейросетью по запросу пользователя. Сгенерированный текст кэшируется по хешу содержимого и перегенерируется только при изменении файла; в интерфейсе он помечен как автоматический.

## 7. Интерфейс (UI)

Интерфейс — отдельное десктопное приложение в духе Obsidian: слева дерево, в центре граф или файл во вкладках, справа сведения о выбранном узле. Всё, что видит нейросеть, человек может увидеть и проверить здесь же.

### 7.1. Общая раскладка

| Зона | Содержимое |
| --- | --- |
| Левая боковая панель | Переключатель вкладок: Файлы, Поиск, Закладки, Проблемы; ниже — дерево проекта |
| Центральная область | Вкладки с разбиением на панели: граф, файл, карта проекта, отчёт; вкладки можно перетаскивать и закреплять |
| Правая боковая панель | Инспектор выбранного узла: свойства, связи, обратные ссылки, оглавление файла |
| Нижняя строка состояния | Состояние индекса, число файлов и узлов, подключённые клиенты MCP, расход токенов за сессию |
| Верхняя полоса | Название проекта, переключатель проектов, кнопки: поиск, подключить к нейросети, экспорт отчёта |

Панели можно скрывать, менять их ширину, а раскладку сохранять под именем.

Схема показывает расположение зон; в центре как пример открыт граф с выделенным узлом-хабом и пунктирной связью с низкой уверенностью.

### 7.2. Дерево файлов

- Иерархия каталогов и файлов с иконками по типу и индикаторами: изменён в git, содержит проблемы разбора, закрыт для нейросети.
- Разворот файла показывает его символы (классы, функции) вложенными узлами.
- Рядом с узлом необязательный бейдж с рангом или числом входящих связей.
- Контекстное меню: открыть, показать на графе, закрыть для нейросети, добавить в исключения, скопировать путь.
- Фильтр по имени и по виду узла в верхней части панели.

### 7.3. Граф

1. **Режимы:** глобальный граф проекта; локальный граф выбранного узла с глубиной 1–3 шага; граф модулей (агрегированный).
2. **Узлы:** цвет по виду (каталог, файл, класс, функция, тест, документ), размер по рангу, яркость по свежести изменений.
3. **Рёбра:** разные стили для видов связей; пунктир для связей с низкой уверенностью; направление стрелкой.
4. **Фильтры:** по видам узлов и рёбер, по языку, по модулю, по давности изменений, скрыть тесты, скрыть сгенерированное.
5. **Группы:** модули отмечаются цветными областями; группы можно сворачивать в один узел.
6. **Подсветка нейросети:** узлы, которые клиент запрашивал в выбранной сессии, подсвечиваются; видно, какие части проекта «изучены», а какие нет.
7. **Управление:** масштаб колесом, перетаскивание, выделение рамкой, клик — инспектор, двойной клик — открыть файл, клавиша `L` — переключить локальный режим.
8. **Раскладка:** силовая (ForceAtlas2) с настройкой отталкивания и длины рёбер, закрепление позиций вручную, сохранение раскладки.
9. **Производительность:** до 5 000 видимых узлов в детальном виде; выше этого порога включается агрегированный вид по модулям с подгрузкой при приближении.
10. **Экспорт изображения:** PNG и SVG текущего вида.

### 7.4. Просмотр файлов

- Режим только для чтения с подсветкой синтаксиса, номерами строк и сворачиванием блоков.
- Над кодом строка «хлебных крошек»: путь, класс, функция; клик по символу в оглавлении прокручивает к нему.
- Над функцией встроенная подсказка: число вызывающих, число вызываемых, связанный тест; клик раскрывает список.
- Клик по имени вызова или импорта переходит к определению (если связь определена в индексе); `Alt+←` возвращает назад.
- Markdown-файлы открываются в режиме просмотра заметки: рендер, оглавление, внутренние ссылки и блок «обратные ссылки» (кто упоминает этот документ).
- Кнопка «Открыть во внешнем редакторе» запускает редактор по умолчанию на нужной строке.
- Над файлом можно включить подсветку «что из этого файла нейросеть уже читала»: фрагменты из журнала вызовов выделяются полосой слева.

### 7.5. Поиск и командная палитра

- `Ctrl/Cmd+P` — быстрый переход к файлу или символу по нечёткому совпадению.
- `Ctrl/Cmd+Shift+F` — поиск по проекту: имена, сигнатуры, докстринги, текст; результаты сгруппированы по файлам с фрагментом контекста.
- `Ctrl/Cmd+K` — командная палитра: все действия приложения (переиндексировать, экспорт отчёта, подключить клиент).
- Тот же поисковый движок обслуживает MCP-инструмент `search`, поэтому результаты у человека и нейросети совпадают.

### 7.6. Инспектор (правая панель)

- Для выбранного узла: вид, путь, строки, сигнатура, докстринг, ранг, число токенов, дата последнего изменения, частота изменений.
- Списки связей: входящие и исходящие по видам, с уровнем уверенности; клик показывает связь на графе.
- Раздел «Запрашивала нейросеть»: когда и каким инструментом узел попадал в ответы.
- Действия: закладка, закрыть для нейросети, показать на графе, сформировать заметку.

### 7.7. Панель расхода токенов

- Сводка по сессии: сколько токенов отдано нейросети, сколько ушло бы на чтение тех же файлов целиком (базовая линия), оценка экономии в процентах.
- График по времени и разбивка по инструментам: какие вызовы самые «тяжёлые».
- Список самых дорогих ответов с возможностью открыть их в журнале.
- Выбор клиента и периода, экспорт в CSV.

### 7.8. Журнал вызовов нейросети

- Лента вызовов: время, клиент, инструмент, параметры, число токенов, затронутые узлы.
- Клик по записи открывает ответ в том виде, в каком его получил клиент, и подсвечивает узлы на графе.
- Фильтры по клиенту, инструменту, периоду и размеру ответа; поиск по тексту.
- Кнопки: очистить журнал, экспортировать, отключить сессию клиента.

### 7.9. Экспорт отчёта в Markdown

Кнопка «Экспорт отчёта» в верхней полосе, пункт командной палитры и команда `atlas report` создают один Markdown-файл: что это за проект, как он устроен и что в нём и вокруг него происходило. Отчёт можно положить в репозиторий, отправить коллеге или дать нейросети как первичный контекст.

**Диалог экспорта.** Пользователь выбирает:

1. Состав разделов (флажки): обзор проекта, структура, ключевые модули, зависимости, активность, использование нейросетью, проблемы индекса.
2. Период для разделов об активности: сегодня, 7 дней, 30 дней, с даты, весь срок.
3. Глубину дерева структуры (по умолчанию 3 уровня) и лимит размера отчёта в токенах (по умолчанию 4 000) — чтобы файл можно было целиком отдать нейросети.
4. Источник описаний: только извлечённые из кода и README (по умолчанию) или сгенерированные нейросетью (требует подтверждения, см. раздел 10.4).
5. Что учитывать: исключить закрытые для нейросети пути (включено по умолчанию), скрыть абсолютные пути, скрыть имена авторов.
6. Место сохранения: файл рядом с проектом (`ATLAS_REPORT.md`), в выбранную папку или копирование в буфер обмена. Перед сохранением показывается предпросмотр с возможностью править текст.

**Содержимое отчёта.**

| Раздел | Что в нём | Откуда берётся |
| --- | --- | --- |
| Шапка | Название, дата и время формирования, версия Atlas, версия индекса, состояние (`fresh`/`stale`) | Метаданные индекса |
| Что это за проект | Назначение в 2–5 предложениях, основной язык, размер: файлы, строки, символы | README, манифесты (`package.json`, `Cargo.toml`, `pyproject.toml`), статистика индекса |
| Структура проекта | Дерево каталогов до выбранной глубины с однострочным описанием модулей и числом файлов | Дерево узлов, докстринги и README модулей |
| Ключевые модули и точки входа | Топ узлов по рангу, хабы, точки входа, главные классы | Ранжирование графа |
| Зависимости | Связи между модулями в виде списка и диаграммы Mermaid; циклы | Рёбра `imports` и `calls` |
| Что было сделано | Изменения за период: список коммитов по темам, затронутые модули, самые изменяемые файлы | Git и метаданные `file_meta` |
| Работа нейросети | Какие клиенты подключались, сколько вызовов, какие модули изучались чаще, оценка экономии токенов | `call_log` |
| Проблемы и ограничения | Файлы с ошибками разбора, исключения, связи с низкой уверенностью, возможный мёртвый код | Индекс |

Если репозитория git нет, раздел «Что было сделано» строится по времени изменения файлов и пропускает коммиты; в тексте отчёта это указано.

**Шаблон файла.**

```markdown
# Отчёт по проекту: <название>

Сформирован: <дата, время> · Atlas <версия> · индекс: fresh

## Что это за проект
Краткое описание, язык, размер: 1 240 файлов, 86 000 строк.

## Структура проекта
- src/ — исходный код (420 файлов)
  - api/ — HTTP-обработчики
  - core/ — доменная логика
- tests/ — тесты (180 файлов)

## Ключевые модули и точки входа
Список по рангу с путями и ролью.

## Зависимости
Диаграмма Mermaid и список циклов.

## Что было сделано (за 30 дней)
Темы изменений, затронутые модули, горячие файлы.

## Работа нейросети
Вызовы, изученные модули, оценка экономии токенов.

## Проблемы и ограничения
Ошибки разбора, исключения, связи с низкой уверенностью.
```

**Правила формирования.**

- Отчёт детерминирован: при неизменном индексе, периоде и настройках получается один и тот же текст, кроме строки даты. Это позволяет хранить отчёты в репозитории и сравнивать их.
- Весь текст берётся из индекса, git и журнала; ничего не выдумывается. Если данных для раздела нет, раздел пропускается, а не заполняется общими словами.
- Лимит размера соблюдается сокращением по рангу: сначала уходят детали малозначимых узлов, структура верхних уровней остаётся.
- Пути в отчёте относительные от корня проекта; секреты и закрытые пути не попадают в текст.
- Форматы: Markdown (основной); дополнительно HTML и JSON с теми же данными для автоматической обработки.
- Возможна подготовка отчёта по расписанию (например, при закрытии проекта) и сохранение истории отчётов в `.atlas/reports/` с датой в имени.

### 7.10. Настройки

- **Проект:** корень, исключения, закрытые пути, язык описаний, лимиты размера файла.
- **Индекс:** состояние, переиндексация, очистка, расположение базы.
- **Граф:** веса ранжирования, пороги хабов, параметры раскладки.
- **MCP:** транспорт, токен, бюджеты по умолчанию, список подключённых клиентов.
- **Отчёты:** состав разделов и период по умолчанию, расписание, папка сохранения.
- **Приватность:** журнал, срок хранения, маскирование секретов, генерация описаний нейросетью.
- **Вид:** тема, шрифты, масштаб, язык интерфейса.

### 7.12. Первый запуск

1. Приветствие и выбор папки проекта.
2. Показ найденных языков и предложенных исключений с возможностью поправить.
3. Индексация с индикатором прогресса; граф появляется по мере готовности.
4. Предложение подключить нейросеть: выбор клиента, готовый фрагмент конфигурации, проверка соединения кнопкой «Проверить».
5. Подсказка про экспорт отчёта и закрытие путей от нейросети.

## 8. Интерфейс для нейросетей (MCP)

Atlas работает как локальный MCP-сервер: любой клиент с поддержкой протокола (Claude, редакторы, агенты) получает набор из семи компактных инструментов. Инструментов намеренно мало: описание каждого стоит токенов в контексте клиента.

### 8.1. Подключение

- Транспорт по умолчанию: stdio (клиент сам запускает процесс `atlas mcp`). Дополнительно: локальный HTTP на `127.0.0.1` с токеном доступа для клиентов, которые не умеют запускать процессы.
- Кнопка «Подключить» в интерфейсе показывает готовый фрагмент конфигурации для популярных клиентов и копирует его в буфер обмена.
- Один экземпляр приложения обслуживает несколько проектов; клиент указывает проект параметром или получает активный по умолчанию.
- Сервер работает и при закрытом окне интерфейса (фоновый процесс в области уведомлений).

### 8.2. Инструменты

| Инструмент | Что делает | Типичный ответ |
| --- | --- | --- |
| `overview` | Карта проекта (L0) или модуля (L1) с рангами | Дерево модулей, 1 строка на модуль |
| `search` | Гибридный поиск по именам, сигнатурам, докстрингам и путям | Список из N символов: путь:строка, вид, сигнатура |
| `outline` | Сигнатуры и докстринги файла (L2) | Список символов файла |
| `read` | Тело символа или диапазона строк (L3) с режимом сжатия | Код с номерами строк |
| `neighbors` | Окружение символа (L4): кто вызывает, что вызывает, тесты, наследники | Списки с указанием уверенности связи |
| `context_for` | Составной инструмент: символ, сигнатуры его зависимостей, вызывающие, связанный тест | Один пакет вместо пяти вызовов |
| `status` | Состояние индекса: свежесть, число файлов, ошибки разбора, исключения | Короткая сводка |

### 8.3. Бюджеты и усечение

- У каждого инструмента есть параметр `max_tokens` (значение по умолчанию задано для инструмента и ограничено сверху настройкой проекта).
- Если результат больше бюджета, он обрезается по рангу, а в конце добавляется строка вида «показано 10 из 143, уточните запрос или добавьте offset».
- Режимы `read`: `signature` (только сигнатура), `doc` (сигнатура и докстринг), `folded` (тело с вложенными блоками, свёрнутыми в `...`), `full` (всё тело).
- Повторный запрос того, что уже выдавалось в этой сессии, возвращает короткое «уже показано выше» с номером вызова, если пользователь не запросил принудительно.

### 8.4. Формат ответов

- Плотный текст вместо JSON там, где это возможно: строки `путь:строка  вид  имя(сигнатура)`, разделитель — табуляция.
- Длинные пути в рамках одного ответа заменяются короткими псевдонимами (`@1`, `@2`) с таблицей соответствия в начале.
- Каждый ответ содержит заголовок из одной строки: проект, состояние индекса (`fresh` или `stale`), число токенов ответа.
- Ошибки возвращаются короткими и с подсказкой: «символ не найден; похожие: …».

### 8.5. Права

Все инструменты только читают. Запись в проект через MCP в первой версии не предусмотрена. Пути из списка исключений недоступны для всех инструментов, включая `search` и `read`.

## 9. Оптимизация токенов

Экономия складывается из пяти механизмов. Первые два дают основную часть эффекта, остальные закрывают частные случаи. Все механизмы включены по умолчанию и отключаются в настройках проекта по отдельности, чтобы их вклад можно было измерить.

| № | Механизм | Как работает | Приоритет |
| --- | --- | --- | --- |
| 1 | Составные инструменты | `context_for` возвращает за один вызов то, что иначе потребовало бы 4–5 вызовов; меньше раундтрипов — меньше повторной оплаты контекста | Высокий |
| 2 | Бюджеты и усечение | Любой ответ ограничен по токенам и сортируется по рангу; пагинация вместо потока данных | Высокий |
| 3 | Режимы чтения | Сигнатура, докстринг, свёрнутое тело, полное тело: модель запрашивает минимум | Высокий |
| 4 | Фильтр вывода команд | Опциональный прокси `atlas run <команда>` сжимает вывод сборок, тестов и логов до ошибок и ключевых строк | Средний |
| 5 | Дедупликация в сессии | Уже показанные куски заменяются ссылкой на предыдущий вызов | Средний |

### 9.1. Фильтр вывода команд

- Оставляет строки с ошибками и предупреждениями, итоговую сводку и по 3 строки контекста вокруг каждой ошибки.
- Схлопывает повторяющиеся строки в одну с счётчиком (`×42`).
- Убирает пути из каталогов зависимостей и ANSI-коды.
- Полный вывод сохраняется на диск, а в ответ добавляется идентификатор, по которому его можно запросить целиком.

### 9.2. Кэширование на стороне клиента

Описания инструментов и карта проекта L0 формируются стабильно: один и тот же проект при неизменном индексе даёт байт-в-байт одинаковый текст. Это позволяет клиентам использовать кэширование промптов провайдера. Любое изменение порядка или формулировок в описании инструментов считается значимым изменением и записывается в журнал изменений версии.

### 9.3. Сжатие истории

Инструмент `status` возвращает компактную сводку «что уже выяснено в сессии» (список просмотренных символов и принятых решений, которые клиент сам отметил). Клиент может использовать её вместо длинной истории вызовов.

### 9.4. Измерение

Приложение считает токены двумя способами: оценка по размеру текста при выдаче и сравнение с «базовой линией» — сколько токенов ушло бы на чтение тех же файлов целиком. Результаты показываются на панели расхода (раздел 7.7) и экспортируются в CSV для методики замера из раздела 14.

## 10. Безопасность и приватность

Atlas видит весь код проекта и отдаёт его фрагменты внешнему клиенту, поэтому по умолчанию действует принцип минимальных прав: только чтение, только локально, только то, что не исключено явно.

### 10.1. Требования

1. Все данные (индекс, журнал, кэш) хранятся локально; приложение не отправляет код, индекс или телеметрию наружу без явного включения пользователем.
2. Все инструменты MCP только читают. Запись в файлы проекта и выполнение произвольных команд через MCP недоступны.
3. Сервер слушает только `127.0.0.1`; HTTP-режим защищён случайным токеном, который можно перевыпустить в один клик.
4. Любой путь из запроса нормализуется и проверяется: выход за корень проекта (`..`, символические ссылки наружу) отклоняется.
5. Секреты: файлы `.env`, ключи, сертификаты и файлы по шаблонам (`*.pem`, `id_rsa*`, `*.key`) исключены из индекса по умолчанию. Дополнительно значения, похожие на ключи и токены, маскируются в ответах `read` (`***`).
6. Пользователь может пометить пути как «закрытые для нейросети»: они остаются видны в интерфейсе, но не попадают в ответы MCP.
7. Для каждого подключённого клиента ведётся отдельная сессия с понятным именем; сессию можно отключить в интерфейсе мгновенно.

### 10.2. Защита от инъекций через содержимое

Комментарии и документы в проекте могут содержать вредоносные инструкции для нейросети. Atlas не исполняет их и не меняет своё поведение, но помечает ответы с содержимым файлов явным маркером «данные проекта, не инструкции». Ответы инструментов не содержат управляющих конструкций, которые клиент мог бы принять за команды.

### 10.3. Журнал и аудит

- Каждый вызов записывается в `call_log`: время, клиент, инструмент, параметры, размер ответа, затронутые узлы.
- Журнал доступен в интерфейсе (раздел 7.8), экспортируется и очищается по команде пользователя.
- Срок хранения журнала настраивается; по умолчанию 30 дней.

### 10.4. Опциональная генерация описаний

Если пользователь включает описания модулей нейросетью (раздел 6.5), приложение показывает, какой провайдер получит какие файлы, и требует отдельного подтверждения для каждого проекта. По умолчанию функция выключена.

- Полная работа с клавиатуры, видимый фокус, контраст текста не ниже 4,5:1.
- Локализация: русский и английский; строки интерфейса вынесены в файлы переводов.
- Масштабирование шрифтов и интерфейса от 80% до 200%.

- Модульные тесты на парсеры: для каждого языка набор эталонных файлов и ожидаемых символов и связей.
- Интеграционные тесты индексатора на 3–5 реальных открытых репозиториях разного размера.
- Контрактные тесты MCP: схемы инструментов, бюджеты, формат ответов.
- Тесты производительности из таблицы выше запускаются в CI на каждом выпуске.
- Тесты безопасности: выход за корень проекта, символические ссылки, маскирование секретов.

## 12. Технологический стек и структура репозитория

Рекомендуется ядро на Rust и интерфейс на веб-технологиях в оболочке Tauri: получается лёгкое кроссплатформенное приложение с одним бинарником, а тяжёлую работу (разбор, индекс, поиск) делает компилируемый код. Выбор стека подтверждается прототипом (этап 0, раздел 13).

### 12.1. Стек

| Слой | Решение | Почему |
| --- | --- | --- |
| Оболочка приложения | Tauri 2 | Небольшой размер, нативные окна, системный трей, меньше памяти, чем у Electron |
| Ядро | Rust | Скорость индексации, параллелизм, один бинарник без зависимостей |
| Парсинг | tree-sitter + запросы `.scm` на язык | Единый подход ко многим языкам, плагинная модель |
| Хранилище | SQLite (`rusqlite`) + FTS5 | Один файл, транзакции, полнотекстовый поиск без отдельного сервера |
| Обход и игнорирование | крейт `ignore` | Те же правила, что у `.gitignore`, высокая скорость |
| Наблюдатель за файлами | крейт `notify` | Кроссплатформенные события файловой системы |
| Граф и ранжирование | `petgraph`, собственные реализации PageRank и Лувена | Работа с графом в памяти для ранжирования |
| MCP-сервер | Официальный Rust SDK для MCP | Совместимость с клиентами, поддержка stdio и HTTP |
| Интерфейс | TypeScript + Svelte или React | Выбор по опыту команды; требования к UI не зависят от фреймворка |
| Граф-вид | Sigma.js + graphology (WebGL), раскладка ForceAtlas2 в веб-воркере | Тысячи узлов с плавным движением |
| Просмотр кода | CodeMirror 6 (режим только чтения) | Лёгкий, подсветка синтаксиса, переходы по символам |
| Просмотр документов | Рендер Markdown с поддержкой ссылок и обратных ссылок | Режим «заметки» в духе Obsidian |

Отклонения прототипа (этап 0, зафиксированы в README): оболочка — Electron 28 вместо Tauri;
MCP-протокол (JSON-RPC по stdio) реализован вручную, официальный Rust SDK отложен;
HTTP-транспорт MCP не реализован.

### 12.2. Структура репозитория

```text
atlas/
  crates/
    atlas-core/        # модель данных, граф, ранжирование
    atlas-indexer/     # обход, парсинг, наблюдатель, инкрементальное обновление
    atlas-langs/       # запросы tree-sitter по языкам (плагины)
    atlas-store/       # SQLite, миграции, FTS
    atlas-mcp/         # MCP-сервер, инструменты, бюджеты, форматирование ответов
    atlas-cli/         # команды: index, mcp, run, doctor
  app/
    electron/         # оболочка Electron, IPC между UI и ядром Rust
    ui/                # интерфейс: граф, дерево, просмотр, панели
  docs/                # документация, формат ответов MCP, руководство по добавлению языка

  bench/               # сценарии замера токенов и производительности
```

### 12.3. Принципы кода

- Ядро не зависит от интерфейса: всё, что умеет приложение, доступно и из командной строки (`atlas index`, `atlas mcp`, `atlas doctor`). Это упрощает тестирование и работу на серверах.
- Интерфейс общается с ядром через узкий набор команд; тяжёлые данные (граф на тысячи узлов) передаются пакетами и кэшируются на стороне интерфейса.
- Языковые плагины — данные (запросы), а не код: добавление языка не требует пересборки ядра в будущих версиях.

## 14. Метрики успеха и критерии приёмки

Главный вопрос проекта — действительно ли индекс экономит токены без потери качества. Поэтому приёмка опирается на сравнительный замер, а не на ощущения.

### 14.1. Методика замера экономии токенов

1. Берутся 3 проекта разного размера: малый (до 100 файлов), средний (500–2 000), большой (более 5 000).
2. Для каждого составляется набор из 15–20 реальных задач: найти, где обрабатывается функциональность; оценить влияние изменения; добавить поле в модель; найти причину падающего теста; объяснить структуру модуля.
3. Каждая задача выполняется одним и тем же клиентом и моделью в двух режимах: без Atlas (поиск и чтение файлов обычными средствами) и с Atlas.
4. Фиксируются: суммарные токены (вход и выход), число вызовов инструментов, время, правильность результата по заранее заданному критерию.
5. Каждая пара прогонов повторяется не менее 3 раз, чтобы учесть разброс поведения модели; сравниваются медианы.
6. Результат без потери качества: экономия токенов не засчитывается, если доля правильных результатов с Atlas ниже, чем без него.

Сценарии, фиксированные наборы задач и скрипты прогона лежат в каталоге `bench/` и воспроизводимы.

### 14.2. Критерии приёмки

| Критерий | Проверка | Порог |
| --- | --- | --- |
| Экономия токенов | Методика 14.1 на среднем и большом проектах | не менее 40% по медиане |
| Качество | Доля задач, решённых верно, с Atlas и без | не ниже, чем без Atlas |
| Число вызовов | Среднее число вызовов инструментов на задачу | не больше, чем без Atlas |
| Точность индекса | Ручная проверка 200 случайных рёбер `calls` и `imports` на эталонных проектах | не менее 95% верных для связей с уверенностью `certain` |
| Свежесть | Время от сохранения файла до актуального ответа MCP | до 1 секунды |
| Производительность | Таблица раздела 11 на эталонной машине | все значения выполнены |
| Безопасность | Тесты раздела 11.4: выход за корень, симлинки, секреты | все пройдены |
| Отчёт | Экспорт на трёх эталонных проектах | файл формируется за секунды, укладывается в лимит токенов, повторный запуск даёт тот же текст |
| Удобство | Тест с 5 разработчиками: подключить клиент и найти узлы-хабы | задача выполнена без помощи за 10 минут |

### 14.3. Продуктовые метрики после выпуска

- Доля пользователей, подключивших хотя бы одного MCP-клиента в первый день.
- Средняя оценка экономии токенов на панели расхода.
- Доля сессий, в которых нейросеть использует `context_for` вместо серии мелких вызовов.
- Частота экспорта отчётов и доля отчётов, сохранённых в репозиторий.
- Число сообщений об ошибках разбора по языкам.

Сбор любой телеметрии только с явного согласия пользователя (раздел 10.1).

### 15.2. Открытые вопросы

- Распространять приложение бесплатно с открытым кодом или коммерчески? От этого зависит выбор лицензий зависимостей и модель обновлений.
- Нужна ли в первой версии работа с несколькими проектами одновременно в одном окне или достаточно переключения?
- Включать ли в MVP локальные эмбеддинги для семантического поиска или ограничиться FTS5? Решение зависит от результатов этапа 0.
- Нужно ли разрешить нейросети записывать заметки в Atlas (например, «выяснено про модуль X»), чтобы они переживали сессию? Это единственный случай записи через MCP, требует отдельной модели прав.
- Достаточно ли отчёта по git и журналу для раздела «Что было сделано», или нужна ручная ведомость задач? Предполагается первое; уточнить у пользователей.
- Нужен ли режим командной работы (общий индекс на сервере) после выпуска версии 1.0?
